# CI/CD delivery

`delivery.yml` runs on pull requests and pushes to `main`. Backend lint, scoped Python typing, unit tests, frontend lint/types/build, and dependency audits must pass before the disposable PostgreSQL/Redis integration test runs. The integration test starts a real worker, indexes a PDF with the real embedding model, retrieves evidence, and verifies a cited chat response against a deterministic local model stub. Docker builds run only after integration succeeds. Pull requests build images without publishing them. Successful pushes to `main` publish three SHA-tagged images (`backend`, `frontend`, `backup`) to GHCR. A manual `workflow_dispatch` on `main` repeats all checks and builds, then deploys those exact images.

Python Ruff currently gates `backend/app` and the production backup script for fatal errors and unused imports. Mypy gates the new storage, entrypoint, and backup modules while the older application modules' existing type errors are addressed incrementally. TypeScript checks the entire frontend. The security gate audits locked Python runtime dependencies and production npm dependencies for known advisories; it does not replace code review or runtime image scanning.

CI tests a proposed change before it enters `main`. CD promotes the tested SHA image to the VPS. Tags use `sha-<full Git commit SHA>` so deployment can identify the exact source. The production Compose override supplies registry images and `--no-build` prevents rebuilding untested source on the host.

## Enforce the merge gate

In GitHub repository settings, protect `main`: require a pull request and these successful checks: `Backend quality and unit tests`, `Frontend quality and build`, `Dependency security`, `PostgreSQL and worker integration`, and all three `Docker image (...)` matrix checks. Require the branch to be current before merging; prevent bypasses and direct pushes by automation where your GitHub plan permits. A workflow file by itself cannot prohibit merging failed code. Confirm the exact reported check names after the first workflow run before selecting them. Do not require `Production deployment`, because it runs only on manual dispatch.

Create a GitHub `production` environment restricted to `main`. Require a reviewer if available on your repository plan. Configure environment secrets `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_HOST`, and `DEPLOY_USER`, plus environment variable `DEPLOY_PATH` (for example `/opt/ai-knowledge-platform`). Use a dedicated deploy account and key. Record the host's verified SSH host key in `DEPLOY_KNOWN_HOSTS`; do not fetch and trust it during the workflow. Environment secrets are accessible only to the deployment job.

## Prepare the VPS once

Follow [Phase 12](PHASE12_PRODUCTION.md) to provision `.env.production`, `deploy/secrets`, DNS, buckets, and Docker. Set up GHCR read access for the deploy account using a read-only packages token and `docker login ghcr.io`; keep the token on the VPS, outside the repository. If images are publicly readable, no token is needed. Install `curl` on the host. Make sure the deploy user can run Docker Compose and can write `DEPLOY_PATH`. The workflow uploads only reviewed Compose/proxy/deployment files; it never uploads secrets or `.env.production`.

For the first release, run the manual workflow from `main` after the GitHub environment and VPS are ready. A fresh deployment has no previous image to roll back to. Every deployment writes an offsite PostgreSQL backup before applying migrations; successful deployments also write `.deployed-image-tag`. The script waits for container health and retries `https://APP_DOMAIN/api/ready`; on a failed startup or health check it restores the previous application image tag. It **does not reverse database migrations**. Make schema changes backward compatible across the current and previous images, or restore the pre-migration backup into a fresh database following the Phase 12 runbook. A successful container health check does not prove model-provider or object-storage availability; perform an upload/chat/research smoke test after release.

Use GitHub Actions → Delivery → Run workflow on `main` to deploy. Check the `Production deployment` job and production health afterward. To intentionally redeploy an older version, use its `sha-...` tag with the deployment script on the VPS only after confirming schema compatibility and backup availability. Keep the `production` environment approval and server credentials under human control.
